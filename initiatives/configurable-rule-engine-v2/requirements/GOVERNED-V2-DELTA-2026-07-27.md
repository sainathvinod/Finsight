# Governed FinSight V2 Delta Record — 2026-07-27

- **Status:** Human-approved initiative direction; detailed Requirements integration remains Draft pending the independent Requirements PASS
- **Scope:** FinSight configurable-rule-engine V2 only
- **Authority:** HD-01–HD-27, especially HD-02–HD-05 and HD-20–HD-27
- **Parent baseline:** Existing approved FinSight specifications remain unchanged in place
- **Baseline action:** The product-wide change identifier and root-spec integration are assigned only during the governed re-baselining step; this initiative record does not edit the root baseline

## Purpose

This record makes the approved V2 deltas explicit so the initiative and parent specification are read as one consistent product contract during Requirements review. It does not authorize application implementation.

## Approved delta interpretations

1. **Configurable rule selection does not permit ad hoc per-run changes.** Root FR-106 continues to prohibit an actor or AI agent from silently varying a rule set for an individual run. V2 distinguishes the globally effective immutable **Protected Baseline Version** from the immutable workspace-scoped **Rule Set Version** displayed to users. A protected activation creates only a Protected Baseline Version. A new workspace or explicitly approved existing-workspace upgrade derives its Rule Set Version from one exact Protected Baseline Version plus its governed Rule Bindings; an optional/advisory binding change creates a Rule Set Version only for the affected workspace. A Validation Run pins one existing Rule Set Version, and later configuration changes require their governed lifecycle and a successor Review Version/Validation Run.
2. **Runtime rule authority is not specification authority.** A Rule Administrator may manage approved controlled rule definitions through the product's runtime lifecycle. That permission does not amend root specifications, the legacy Rules Catalog, the Constitution, or business-owned financial policy. Those changes retain the parent Constitution's Project Owner and domain/control decision rights.
3. **Protected-candidate preparation and approval are separated.** A Rule Administrator may author and test a protected Draft candidate but cannot activate it. A protected request references an immutable Tested candidate. A different Financial Control Approver authorizes activation and any application to an existing workspace.
4. **The eleven-step workflow is a V2 refinement.** WF-01–WF-11 replaces the earlier eight-step presentation count for this initiative while preserving the Monthly Review in a Box, verification-before-validation, and historical-review principles.
5. **Overall Review Status and RAG are one result.** `Healthy` maps to `On Track (Green)`, `Attention Required` maps to `Needs Attention (Yellow)`, and `Incomplete` maps to `At Risk (Red)`. Both labels originate from the same persisted rule-engine result and versioned status policy.
6. **The inherited verification boundary remains intact.** Explicit Reviewer confirmation consumes a Working Candidate and creates/seals a Review Version/ReviewGeneration at `Data Reviewed`. A `RULESET_REANALYSIS` or `CONFIG_REANALYSIS` generation may begin at `Data Reviewed` only when it inherits the exact verified fingerprint, source fingerprints, extractor/correction basis, and original verification Actor/time; it records the reanalysis initiator separately and never claims that a new verification occurred. The fingerprint-verified reconstructed projection and lineage are the V2 realization of the parent `VerifiedDataset`, the only data input accepted by the deterministic Rules Engine.
7. **Sealed review evidence remains immutable.** A sealed snapshot consists of authoritative generation, verification-basis, source-binding/fingerprint, correction/confirmation, run, result, finding, audit, promotion, and derived-artifact records. It does not mean that normalized workbook rows, a full Working Dataset, a full `VerifiedDataset`, or source workbook bytes are persisted. Reports, exports, and Ask Fin responses created later are separate append-only derived artifacts linked to a sealed Review Version and Validation Run; they do not mutate historical records.
8. **Explicit end-of-life disposal is distinct from mutation.** Ordinary Closed/Archived review actions cannot erase evidence. Root NFR-017's separately initiated, explicitly confirmed whole-scope disposal remains available for a Review Cycle, period, or all stored data and retains only the content-free deletion audit record required by that policy.
9. **The Windows gate does not remove inherited macOS parity.** V2 requires a qualified Windows executable and installer and uses Windows account identity as its default actor source. Parent NFR-028/NFR-029 still require macOS functional parity and identical deterministic results; an authenticated non-Windows platform account maps through the same replaceable Actor boundary.
10. **Review Version is the V2 identity of an inherited ReviewGeneration.** Review ID maps to the inherited ReviewCycle. Before confirmation, mutable intake belongs to a Working Candidate with `Draft` or `Data Uploaded` Review Status and is not a Review Version or ReviewGeneration. Explicit confirmation at `Data Reviewed` creates and seals Review Version N as the user-facing identity of exactly one inherited `ReviewGeneration(sequence_number=N)`. `Data Reviewed` maps to generation `VERIFIED`; `Validation Complete` requires generation `ANALYZED`; `Reviewed`, `Closed`, and `Archived` are append-only operational workflow/disposition states and never move analytical state backward.
11. **Datasets are reconstructed under ADR-012.** FinSight persists source bindings/fingerprints and versioned extractor, correction, reversion, confirmation, verification-basis, and data-fingerprint records. It reconstructs normalized rows, the Working Dataset, and the complete `VerifiedDataset`/Current Validation Value projection from fingerprint-matching source bytes plus those records; it does not persist the complete row stores or source workbook bytes. Missing, mismatched, or extractor-divergent source prevents reconstruction and surfaces the inherited recovery state without changing trusted results.
12. **Working and published generations remain distinct.** A newly created Review Version is the working generation. The first generation auto-publishes only after its complete Validation Run reaches `ANALYZED`. A successor stays working/unpublished until an authorized Reviewer explicitly promotes it at `ANALYZED` or later. Promotion atomically appends prior-to-successor supersession, changes the published pointer, and records actor/time/reason; failed or abandoned work never changes the published generation. Trusted dashboard, analytics, report, export, and Ask Fin defaults use the published generation. The immediate post-validation Review Summary may display a working run only with a prominent `Working — Unpublished` state; it never silently replaces published metrics.
13. **Rerun reasons preserve inherited generation semantics.** Changed source bytes, reviewed Current Validation Values, or extractor basis return work to a Working Candidate and require fresh human confirmation before creating the next generation with `SOURCE_REVERIFICATION` or `EXTRACTOR_REVERIFICATION`. A rule-set or configuration change over an unchanged verified basis creates a working `RULESET_REANALYSIS` or `CONFIG_REANALYSIS` generation that inherits the exact original verification actor/time, verified fingerprint, extractor version, and correction basis while recording the reanalysis initiator separately. Exact replay with unchanged data, rules, and configuration compares a recomputation with retained results and does not create another authoritative generation or run. Promotion is not a rerun.
14. **Abandonment and export identity remain inherited.** `Active`/`Abandoned` is an orthogonal, explicit, audited, non-destructive ReviewCycle disposition under ADR-014; it does not replace the seven-state V2 Review Status. Every export remains an immutable one-generation ADR-015 artifact with the full generation/run/fingerprint/version manifest and an unambiguous creation-time working, published, historical, or superseded label.

## Gate effect

The independent Requirements reviewer must assess the V2 delta registers using these interpretations. A PASS fulfills only the HD-27 Requirements-review condition and permits Architecture to begin. Product-wide baseline integration still requires the normal governed change and re-baselining records. Application implementation remains blocked until the Architecture, rule-engine design, persistence model, UX/UI, and technical implementation plan are reviewed and approved.
